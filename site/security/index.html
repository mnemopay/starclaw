StarClaw does not prevent prompt injection. It assumes the model will sometimes be steered by hostile content. It limits what that can cost you: risky actions need a human, who is shown the exact action and where the untrusted content came from, and everything is provable afterwards.

This is an alpha. It has had no external review or fuzzing. Do not treat it as secure, production-ready or consumer-ready.

This page restates the "What is and is not protected" and "Known limits" sections of the README, and parts of SECURITY.md. If this page and those files ever disagree, the files in the repository win.

What is and is not protected

ThreatResult
Generated code spawns processes, loads addons/workers/WASI, opens sockets, reads or writes outside the workspace, signals other processesBlocked and probe-verified on Node 25.9.0 / Windows, in the process layer and (when available) again by the container layer. Details: starclaw doctor.
Generated code tries to reach the host (files, network, docker socket, environment, other processes)Container layer: no mounts, no network, no capabilities, non-root, read-only root, memory and process caps. Probe-verified from the host side on Docker Desktop (WSL2).
Injected text makes the agent exfiltrate data, run commands or spendNot prevented. Requires human approval once the session is tainted; the human sees the provenance.
You approve something harmfulNothing stops you. Approved host commands run with your full privileges.
Someone edits the audit log or memory without the signing keyDetected.
Someone who can read .starclaw/audit.keyCan forge both. The key sits next to the data.
Malicious code that finds a Node permission-model bypassWith the container layer: confined by the container instead. Without it: not covered (Node documents the model as a "seat belt").
Malicious code that finds a Linux kernel or container-runtime escapeNot covered. Containers share the kernel (on Docker Desktop: the WSL2 VM's). For hostile multi-tenant use, put gVisor, Kata or Firecracker underneath.

Known limits

  • The sandbox layers were tested on Windows 11 x64 with Node 25.9.0. On Linux and macOS, CI tests installation and startup only, not the sandbox layers (the startup probe will tell you what it finds on your machine).
  • Node.js 25.9.0 or newer is required. On Node 24.22.3 and 22.23.5 the permission model still allows outbound network, so the probe fails and StarClaw refuses to run generated code. Node 25.0 to 25.8 were not tested; the runtime probe decides.
  • Containers are not VMs: they share the host kernel. Passing an alternative OCI runtime (such as runsc) is supported by a setting, but that path is untested.
  • The container does not protect .starclaw/audit.key if the host itself is compromised. The key lives on the host.
  • Without Docker, the process layer is Node's permission model plus JavaScript-level hardening plus a probe: a seat belt, not a VM.
  • Docker was only tested on Windows 11 with Docker Desktop (Linux containers, WSL2).
  • No payment rail is included. Real money movement is unimplemented and untested.
  • tools.runCommand runs approved commands unsandboxed on the host.
  • Memory and audit integrity are only as strong as the secrecy of the key in .starclaw/.
  • Slack, Discord and the browser tools were verified only against local fakes, not the real services.
  • Windows installers are not code-signed yet. Check each one against the release's SHA256SUMS.txt; see the download page and the code signing policy.

Threat model in short

Considered: hostile content that tries to steer the model; a misbehaving or compromised model that emits arbitrary code; a local attacker who can write to the state directory but does not have the signing key.

Not considered: an attacker who can read the signing key or run code as your user outside StarClaw; a malicious maintainer or dependency; physical access; side channels.

The audit trail and residual risks

  1. Prompt injection works against the model. StarClaw only gates what the model can do. A human who approves is the last line of defence.
  2. The process layer is a seat belt. A container or kernel escape is not covered.
  3. Approved host commands are unsandboxed.
  4. Key and state files are only as safe as your user account.
  5. Only one OS and Node combination was tested. No external review or fuzzing was done.

Reporting a problem

SECURITY.md asks that vulnerabilities be reported privately to the maintainer, and that exploits not be filed as public issues. Report them to security@starclaw.dev.
